## Реализация

* **`task-validation.js`:** проверяет, что `req.body` является обычным JSON-объектом, отсекает запрещённые (`id`, `completed` при POST) и неизвестные поля (включая `__proto__` через `Object.create(null)` для `details`), обрезает `title` через `.trim()` и контролирует длину 1–100 символов, допустимость `priority` и существование `categoryId`. Все ошибки собираются в единый словарь `details` с исключением `ApiError(400, 'VALIDATION_ERROR', ...)`.
* **`store.js`:** управляет копиями задач в памяти и монотонным счётчиком `nextId` (начинающимся с `35`). `createTask` создаёт запись с серверным `id` и `completed: false`; `updateTask` объединяет только проверенные поля, сохраняя неизменным `id`; `deleteTask` удаляет запись без уменьшения `nextId`.
* **`write-routes.js`:** подключает `jsonBody` и `requireTask(store)`, выполняет валидацию до обращения к хранилищу (исключая частичные изменения при ошибке) и отправляет ответы `201 Created` с заголовком `Location`, `200 OK` или `204 No Content`.

## Контракт

* **Создание (`POST /api/tasks`):** статус `201 Created`, заголовок `Location: /api/tasks/35`, тело `{"data": {...}}`.
* **Обновление (`PATCH /api/tasks/4`):** статус `200 OK`, тело `{"data": {...}}`.
* **Удаление (`DELETE /api/tasks/4`):** статус `204 No Content`, пустое тело.
* **Различие `INVALID_JSON` и `VALIDATION_ERROR`:** `INVALID_JSON` выбрасывается парсером тела при синтаксически повреждённом или пустом JSON; `VALIDATION_ERROR` выбрасывается валидатором при корректном JSON, нарушающем бизнес-правила полей или схему объекта.

Пример ответа ошибки 400 (`POST /api/tasks` с пробельным названием):
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Данные не прошли проверку.",
    "details": {
      "title": "Длина названия должна быть от 1 до 100 символов."
    }
  }
}
```

## Интеграция клиента

Клиент из ПР8 обращается к `http://127.0.0.1:5505/api`; изменения исходного кода клиента ПР8 не потребовались. При ошибке валидации на сервере или сбое мутации форма сохраняет введённый черновик и выводит сообщение ошибки мутации отдельно от ошибок GET.

## Исправленный дефект

В реализации `task-validation.js` словарь ошибок `details` создан через `Object.create(null)`, а наличие полей проверяется через `Object.hasOwn(value, ...)`, что предотвращает потерю ошибки при передаче специального имени `__proto__` в JSON и гарантирует прохождение теста на prototype pollution.

## Контрольные вопросы

1. *Зачем валидация на сервере при наличии HTML `required`?* — Клиентскую проверку можно обойти (DevTools, `curl`, Postman), поэтому сервер должен независимо проверять все входящие данные.
2. *Чем `400` отличается от `415` и `413`?* — `400` означает неверный JSON или нарушение правил полей, `415` — неверный `Content-Type` или кодировку, `413` — превышение лимита размера тела (16 КиБ).
3. *Почему `id` и `completed` нельзя принимать при `POST`?* — Идентификатор и начальный статус контролируются сервером для гарантии целостности и уникальности данных.
4. *Как в `PATCH` отличить непереданное поле от переданного `false`?* — Проверкой существования собственного свойства через `Object.hasOwn(value, 'completed')`.
5. *Зачем заголовок `Location` в `201 Created`?* — Указывает URI созданного ресурса (`/api/tasks/35`) по стандарту REST.
6. *Почему нельзя уменьшать `nextId` при `DELETE`?* — Удаление записи не должно приводить к повторной выдаче прежних идентификаторов новым ресурсам.
