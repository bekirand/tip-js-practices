## 3. Реализация

### 3.1. HTTP-клиент

Модуль `src/api-client.js` реализует фабрику `createApiClient`. Поддерживаются HTTP-методы `GET`, `POST`, `PATCH`, `DELETE`.
- При наличии тела запроса объект сериализуется в JSON и выставляется заголовок `Content-Type: application/json`.
- Для всех запросов выставляется заголовок `Accept: application/json`.
- Для успешных ответов со статусом 204 (No Content) возвращается значение `null` без вызова `response.json()`.
- При получении кодов ошибок 4xx/5xx клиент извлекает тело ошибки и выбрасывает специализированное исключение `ApiError` с полями `kind: "http"`, `status` и деталями ответа.
- Таймаут запросов реализован через `AbortSignal.timeout(timeoutMs)` с поддержкой объединения через `AbortSignal.any` с внешним сигналом отмены пользователя, позволяя точно отличать таймаут (`kind: "timeout"`) от отмены (`kind: "aborted"`).

### 3.2. Доменный API

Модуль `src/task-api.js` (`createTaskApi`) реализует абстракцию операций над задачами:
- `getTasks(filters)` — получение списка с нормализацией параметров поиска и фильтрации;
- `getTaskById(id)` — чтение задачи по идентификатору;
- `createTask(draft)` — отправка POST-запроса на создание задачи;
- `updateTask(id, patch)` — частичное обновление задачи через PATCH;
- `deleteTask(id)` — удаление задачи (DELETE);
- `getCategories()` — получение справочника категорий;
- `loadInitialData(filters)` — параллельная загрузка задач и категорий через `Promise.all`;
- `resetData()` — сброс данных API к исходному состоянию.

Схема ответа проверяется во вспомогательных функциях валидации: убеждаемся в наличии обязательных полей (`id`, `title`, `priority`, `completed`, `categoryId`), корректности их типов данных и структуры метаданных пагинации.

### 3.3. Состояния интерфейса

В контроллере приложения `src/app-controller.js` реализованы 4 взаимоисключающих состояния UI:
- `loading`: показывается индикатор загрузки, скрываются карточки, сообщения об ошибках и пустоте;
- `ready`: отображается список карточек задач при наличии элементов;
- `empty`: активируется при успешном ответе сервера с пустым массивом задач (`tasks.length === 0`), список очищается и показывается сообщение об отсутствии задач;
- `error`: показывается блок с сообщением об ошибке и кнопка повтора запроса.

При повторной загрузке состояние переходит в `loading`. Ошибки отмены (`aborted`) от предыдущих устаревших запросов перехватываются и не приводят к показу экрана ошибки.

### 3.4. Изменение данных

- **Создание:** данные формы проходят валидацию функцией `validateTaskDraft`. При успехе элементы управления формы блокируются, отправляется `POST /api/tasks`, форма очищается, и список задач перезапрашивается с сервера для синхронизации с текущими фильтрами.
- **Редактирование:** клик по кнопке редактирования переводит форму в режим правки с заполнением полей выбранной задачи. При отправке выполняется `PATCH /api/tasks/:id` и повторный запрос списка.
- **Смена статуса:** клик по чекбоксу задачи отправляет `PATCH /api/tasks/:id` со значением `{ completed: !currentStatus }` и перезапрашивает список.
- **Удаление:** клик по кнопке удаления отправляет `DELETE /api/tasks/:id` (204 No Content), после чего список обновляется.

### 3.5. Защита от устаревшего ответа

Для защиты от состояния гонки (race conditions) при быстрой смене фильтров и повторных запросах:
1. При каждом новом запросе списка вызывается `abort()` у предыдущего активного экземпляра `AbortController`.
2. Ведется счетчик/токен текущей загрузки (`currentRequestId`). Если завершившийся асинхронный запрос имеет устаревший токен, его результат игнорируется и не обновляет интерфейс.

## 6. Ответы на контрольные вопросы

1. *Почему `fetch` не отклоняет Promise при ответе 404?*<br>
   Функция `fetch` отклоняет Promise только в случае сетевого сбоя (network failure), разрыва соединения или нарушения CORS-политики — когда HTTP-ответ вообще не был получен клиентом. Ответ с HTTP-кодом 404 (Not Found) является полностью сформированным валидным HTTP-ответом сервера, поэтому Promise успешно разрешается объектом `Response`, у которого свойство `ok` равно `false`, а свойство `status` равно `404`.

2. *Почему ответ 204 нельзя разбирать вызовом `response.json()`?*<br>
   HTTP-статус 204 No Content по стандарту означает успешную обработку запроса при полном отсутствии тела ответа (Content-Length равен 0 или заголовок отсутствует). Попытка вызвать метод `response.json()` на пустом потоке данных приводит к синтаксической ошибке разбора JSON (`SyntaxError: Unexpected end of JSON input`).

3. *Чем состояние `empty` отличается от `error`?*<br>
   Состояние `empty` — это штатный успешный результат (HTTP 200 OK), означающий, что запрос выполнен без сбоев, но по заданным критериям фильтрации не найдено ни одного элемента (пустой массив данных). Состояние `error` возникает при нештатных сбоях (сетевая ошибка, таймаут, серверная ошибка 5xx или клиентская ошибка 4xx), когда данные получить не удалось, и интерфейс должен уведомить пользователя о сбое и предложить повторить действие.

4. *Зачем отменять предыдущий запрос при смене фильтров?*<br>
   Для предотвращения состояния гонки (race condition). Если пользователь быстро меняет фильтры, запросы отправляются асинхронно. Из-за вариативности сетевых задержек первый запрос может завершиться позже второго. Без отмены предыдущего запроса его запоздалый ответ перетер бы более свежие и актуальные данные второго запроса.

5. *Почему после мутации список повторно запрашивается у API?*<br>
   Повторный запрос обеспечивает соответствие принципу «единственного источника правды» (Single Source of Truth) на сервере. При изменении данных на бэкенде могут пересчитываться связанные поля, пагинация, сортировка или серверная фильтрация. Повторная выборка гарантирует полную синхронизацию состояния клиента с сервером.
