## Полученный результат

Реализован кастомный хук `useTaskData`, связывающий React-интерфейс с HTTP API. Приложение загружает задачи и категории с сервера с передачей фильтров в query-параметрах, поддерживает создание, редактирование, смену статуса, удаление и сброс набора, корректно обрабатывает состояния загрузки/ошибки, отменяет устаревшие запросы и не допускает двойной отправки мутаций. Данные хранятся в памяти запущенного процесса API и сохраняются между перезагрузками страницы, пока работает сервер.

## Архитектура

* **Слои:** `api-client.js` (HTTP-транспорт `fetch`, тайм-ауты, разбор ошибок `ApiError`, статус 204) → `task-api.js` (доменные методы и валидация схем ответа) → `useTaskData.js` (синхронизация эффектов и мутаций с React) → `App.jsx` и компоненты (`TaskFilters`, `TaskForm`, `TaskList`).
* **Зависимости и cleanup:** эффект загрузки зависит от `[api, q, completed, priority, categoryId, revision]`. При каждом новом запуске создаётся свой `AbortController` и локальный флаг `active`; cleanup переводит `active = false` и вызывает `controller.abort()`.
* **Служебные ссылки (`useRef`):** `mountedRef` контролирует жизненную активность компонента (учитывая двойной цикл `StrictMode`), а `mutationAbortRef` немедленно блокирует синхронный повтор мутаций до начала `await` и отменяет запрос при размонтировании.
* **Отличия от ПР7:** убран локальный массив задач и локальная фильтрация `selectTasks`; id назначаются сервером; `onSave` стал асинхронным (`Promise<boolean>`); статистика отображает `meta.total` для текущей серверной выборки.

## Загрузка и изменения

* **Подавление устаревших ответов:** проверка `!active || !mountedRef.current` в `try` и `!active || !mountedRef.current || controller.signal.aborted` в `catch` не позволяет запоздалому ответу или отмене затереть свежий снимок.
* **Блокировка повторной мутации:** `mutationAbortRef.current` устанавливается синхронно до первого `await`, поэтому второй быстрый клик сразу возвращает `false`.
* **Разделение ошибок мутации и GET:** ошибка POST/PATCH/DELETE попадает в `mutationError` и возвращает `false`, а ошибка последующего GET попадает в `error` (`status = 'error'`), не отменяя уже подтверждённое сервером сохранение.
* **Черновик при ошибке:** так как `saveTask` возвращает `false`, форма сохраняет введённый пользователем черновик.

## Контрольные вопросы

1. *Зачем для загрузки нужен эффект?* — Запрос к внешнему API — это побочный эффект, он должен выполняться после рендера и реагировать на изменение зависимостей.
2. *Когда вызывается cleanup?* — Перед следующим запуском эффекта при изменении зависимостей и при размонтировании компонента.
3. *Почему callback эффекта не `async`?* — `async`-функция возвращает `Promise`, а React ожидает либо `undefined`, либо синхронную функцию очистки.
4. *Какие зависимости нужны и почему нет `snapshot`?* — Поля фильтров, `api` и `revision`; включение результата `snapshot` привело бы к бесконечному циклу запросов.
5. *Почему важна стабильная ссылка `api`?* — Пересоздание объекта на каждом рендере вызывало бы перезапуск эффекта при любом обновлении состояния.
6. *Зачем кроме `AbortController` проверять актуальность?* — Тестовые моки или буферизированный ответ могут разрешиться после вызова `abort()`.
7. *Почему защита нужна в `catch`?* — При ошибке отменённого запроса нельзя показывать ошибку в UI поверх актуального состояния.
8. *Что проверяет StrictMode?* — Корректность очистки ресурсов и отсутствие утечек/лишних эффектов при повторном монтировании.
9. *Почему `pending` в state недостаточно для двойного клика?* — Состояние обновляется асинхронно на следующем рендере, а два синхронных вызова читают прежнее `false`.
10. *Что означает `true` при ошибке последующего GET?* — Мутация на сервере успешно подтверждена, не нужно повторно отправлять POST.
11. *Почему нельзя повторять POST после тайм-аута?* — Сервер мог уже создать запись, а повтор приведёт к дублированию данных.
12. *Почему смена фильтров не отменяет мутацию?* — Чтение и запись независимы: пользователь уже подтвердил изменение на сервере, прерывать его не нужно.
13. *Что с серверной операцией после отмены ожидания?* — Сервер обычно доводит уже полученный запрос до конца, отменяется только ожидание на стороне клиента.
14. *Чем `meta.total` отличается от размера базы?* — Отражает количество записей, удовлетворяющих текущим фильтрам запроса.
15. *Какие сценарии требуют браузера?* — Реальный CORS, визуальная вёрстка, фокус, `StrictMode` с реальной сетью и работа Vite preview.
